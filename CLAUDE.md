# CLAUDE.md

The ROS 2 package `syncai_robot_state`, written in Rust (`rclrs` 0.8): it aggregates the robot's
status sources into one `syncai_common/RobotState` at 1 Hz. It is a port of
`~/Desktop/Projects/SyncAI-Robot-Workspace/src/syncai_robot_state` (C++ / rclcpp), and **its
external interface must stay identical to the C++ version** (node name `syncai_robot_state`,
executable `robot_state_node`, parameter names, topics, message types, QoS, the `get_mode` client):
`syncai_backend` depends on it. When behaviour is in doubt, the C++ version is authoritative; the
README's "Differences from the C++ version" lists every knowing deviation and must stay complete.

Its sibling is SyncAI-Robot-Driver-Manager (also Rust/rclrs), whose layout and conventions this
repo copies.

**The repo root is the package itself** (`package.xml` and `Cargo.toml` are at the root); the
Workspace pulls it into `src/syncai_robot_state` with vcstool (replacing the C++ version).
`interface.repos` and `.devcontainer/` are only for developing this repo on its own. There is no
Makefile or docker-compose.

## Build and test

Everything runs in the Dev Container `syncai-robot-state` (VS Code Reopen in Container, or
`devcontainer up --workspace-folder .`). The container's `/workspace` is the named volume
`syncai-robot-state_workspace` (holding build / install / log and the `src/syncai_common` that
`postCreateCommand` vcs-imports), and this repo is mounted at `/workspace/src/syncai_robot_state`.
The host has no ROS, so nothing can be compiled there — `cargo fmt` is the only thing that works on
the host, and `cargo check` fails in the `rclrs` build script with "Failed to determine ROS distro".

```bash
docker exec syncai-robot-state bash -lc 'cd /workspace && colcon build --symlink-install --packages-select syncai_robot_state'
docker exec syncai-robot-state bash -lc 'cd /workspace/src/syncai_robot_state && cargo fmt --check'
docker exec syncai-robot-state bash -lc 'cd /workspace/src/syncai_robot_state && cargo clippy --target-dir /workspace/build/.clippy --all-targets'
docker exec syncai-robot-state bash -lc 'cd /workspace/src/syncai_robot_state && cargo test --target-dir /workspace/build/.clippy'
```

- `cargo` commands need one `colcon build` first: `/workspace/.cargo/config.toml` is generated by
  colcon-ros-cargo.
- If `syncai_common` is missing (a fresh volume), run
  `cd /workspace && vcs import < src/syncai_robot_state/interface.repos` in the container.
- Warnings from `/opt/ros2_rust_underlay/...` (rclrs itself) are not ours; ignore them. So are
  cargo's "Patch `<pkg>` was not used in the crate graph" notices — colcon-ros-cargo writes a patch
  entry per package on `AMENT_PREFIX_PATH`, and `ros-env` inlines message crates rather than
  depending on them.
- Before finishing, build / clippy / fmt must have zero warnings and all unit tests must pass.
- CI (`.github/workflows/ci.yml`) runs the same commands: `cargo fmt --check` on the bare runner,
  and `.github/scripts/ci.sh` (vcs import, colcon build, `clippy -- -D warnings`, test) inside the
  Dev Container image built from `.devcontainer/Dockerfile`. Keep the script and this list in step.

### Killing a test node

`pkill -f robot_state_node` run inside `docker exec ... bash -lc '...'` **kills the shell too**,
because the exec's own command line contains that string, and the whole script dies silently with
no output. Use `pkill -x robot_state_node` (matches the process name only). Note also that
`kill`ing the `ros2 run` wrapper leaves the node itself running — two stray nodes publishing at
1 Hz look exactly like one node at 2 Hz.

## Real-robot safety (important)

The dev container uses the host network and `ROS_DOMAIN_ID=2`, the same as the driver manager's
container, so a node started here joins a graph that may include the real robot's. This node only
subscribes and publishes `robot_state` — it sends no commands and nothing here can move the robot —
but when testing with fake `/tf` or `battery_state` publishers, `export ROS_DOMAIN_ID=77` so the
fakes cannot reach anything real.

## Architecture (`src/robot_state_node/`)

| File | Responsibility |
| --- | --- |
| `mod.rs` | Wiring: parameters → publisher → one worker → seven subscriptions + two timers |
| `parameters.rs` | The nine load-time parameters (all read-only), and Hz -> period |
| `state.rs` | The worker payload, sample intake, the latch tick and `build_state()` |
| `subscribers.rs` | The seven subscriptions and their QoS |
| `mode_poll.rs` | The `get_mode` client poll, its in-flight guard and the mode cache |
| `tf.rs` | **Pure** TF buffer + lookup replacing `tf2_ros`; no ROS types, all unit-tested |
| `health.rs` | **Pure** low-battery hysteresis latch; unit-tested |
| `wifi.rs` | **Pure** `WifiStatus` -> `wifi_info` JSON string; unit-tested |

New logic that can be expressed over plain Rust types goes in `tf.rs` / `health.rs` / `wifi.rs`
with unit tests; the ROS messages are converted at the subscription boundary so those tests need
neither a ROS environment nor the robot.

**Threading:** everything runs on ONE rclrs `Worker`, which is why there is no mutex anywhere
except the small one in `mode_poll.rs` that the `get_mode` response callback reaches from the
executor's task pool. The C++ needs two callback groups because `tf2_ros::Buffer::transform()`
blocks; nothing in this port blocks. Do not add a second worker without a blocking callback to
justify it — it would buy a lock and nothing else.

## rclrs pitfalls (all hit in practice)

- **Params YAML keys do not expand wildcards**: only `/**` or the node's full name match.
  `/**/syncai_robot_state` is silently ignored and everything falls back to defaults — including a
  10 Hz publish rate instead of the intended 1 Hz. This package's YAML uses `/**:`.
- **Worker = callback group**: callbacks from `node.create_*` all queue on the executor's single
  thread; callbacks from `worker.create_*` run on that worker's own thread. The callback shape is
  `FnMut(&mut Payload, Msg)`.
- **The log macros take `&Logger`, not `Logger`.** `log_warn!(self.logger, ..)` fails with
  "the trait `ToLogParams` is not implemented for `Logger`"; write `&self.logger`. A
  `self.logger.throttle(d)` argument already works, because the method call auto-refs.
- **`Arc::from(s)` in a parameter builder is ambiguous** when nothing downstream pins the element
  type — use `Arc::<str>::from(s)`.
- **No SIGINT handler**: Ctrl-C ends the process immediately and `Drop` does not run. A process
  backgrounded with `&` in a non-interactive shell script ignores SIGINT; send SIGTERM to stop it.
- **No `prune_pending_requests` on a client.** An abandoned service request's callback stays in the
  request board; `mode_poll.rs` documents what that costs here.
- **`ros-env` versions**: the package uses `ros-env` 0.2 while rclrs uses 0.3 internally, and their
  message types are incompatible. Do not use rclrs helpers that return message types (e.g.
  `Time::to_ros_msg`); build them yourself from `Time::nsec`.
- The `Message` trait under `rclrs::*` is `rosidl_runtime_rs::Message`.
- Message packages do not go in `Cargo.toml` but in `<depend>` in `package.xml`; without it
  `ros_env::<pkg>` does not exist.
- **A fresh image build can fail with "rustc 1.85.0 is not supported"**: rclrs commits no lock
  file, so its dependencies resolve to whatever is newest, and `uuid` already needs rustc 1.89.
  The Dockerfile sets `CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS=fallback` so cargo prefers
  versions whose `rust-version` fits the pinned toolchain. Do not "fix" this by bumping the pin
  alone: `clippy.toml` (`msrv`) and `rustfmt.toml` are written for 1.85.
- **`tf2_msgs` comes from the apt deb, not the underlay.** Contrary to what the driver manager's
  README says about apt message packages, the official `ros-humble-*` interface debs DO ship
  generated Rust bindings at `share/<pkg>/rust` (22 of them in `ros:humble-ros-base`), and
  `tf2_msgs` is the one message package this node uses that the ros2_rust underlay does not rebuild
  and shadow. Verified to build against it with nothing added to the image.
- `launch/` and `params/` are installed to share via `[package.metadata.ros] install_to_share` in
  `Cargo.toml`.

## Conventions

- Everything is written in English: code and config comments (Rust, Cargo.toml, Dockerfile,
  devcontainer.json, toml…), log messages, and docs such as README / CLAUDE.md. Log messages carry
  a `[Module]` prefix (e.g. `[RobotStateNode]`, `[ModePoll]`, `[Parameters]`).
- Formatting follows the root `rustfmt.toml` (max_width 100); Cargo.toml enables
  `unsafe_code = "forbid"` and `clippy::all`.
- Commits use Conventional Commits (`.github/prompt/copilot-commit-message-instructions.md`), in
  English.
- `syncai_common` is another repo that vcstool pulls into the container workspace (it is not in
  this repo); change message definitions in SyncAI-Robot-Interface.
- Known open questions, inherited from the C++ version: `RUNNING` / `ERROR` are never derived,
  `CHARGING` cannot be derived at all, and `low_level_mode` carries no freshness information. The
  README's "Known limits" section records why each one is still open.
